## How I want agents to work here
Steps I've asked agents to take differently from the README or their defaults, collected by memgraph from my past sessions (2026-11-24). Full compressed README: `/home/proto/agent-memory/vault/Readmes/robot-learning.md`. Regenerate with `memgraph readmes --write-agents`; edit outside this block (text inside it is replaced).

1. **Where to run** — Run tests, pipelines, doc-command checks and simulator pictures on the GCP GPU VM (VM=<vm> ZONE=<zone> scripts/gcp_vm.sh ...), across every embodiment including so-100. Never run them on the laptop
   _Instead of:_ The README quick start: run `vlab run` locally (the agent once ran slow CPU pipelines locally) · _Why:_ The laptop is CPU-only and slow (~23 min smoke run versus ~3 min on the L4) — “for testing ideally use a vm” (2026-11-14)
2. **Shared VM** — Work in your own dir on the VM (e.g. ~/rl-verify via git archive + scp + PYTHONPATH). Before stopping, run a separate check (`pgrep -af "[v]lab|[p]ytest"`, nvidia-smi, `ls ~ ~/RUNNING-*`) and leave the VM running if another session is active; never chain check and stop. Don't run in ~/robot-learning's reference runs/
   _Instead of:_ Use the shared checkout and stop the VM when your own job ends · _Why:_ One session's VM stop killed another session's running verify_all, and a later chained stop killed a dreamer run 30 s after it started — “tell me whats happening on the vm currently” (2026-11-14)
3. **Simulator** — Build real2sim and the style-preserving dreamer pipeline in Steel by Skild AI and NVIDIA Newton (Isaac Sim), on the GCP VM
   _Instead of:_ Use MuJoCo / the LeRobot sims the repo already ships, or set up locally · _Why:_ Explicit user correction — “Not mujoco, it has to be done in steel by skild ai and nvidia newton in isaac sim” (2026-11-24)
4. **VM lifecycle** — Stop the VM when work is done and delete idle VMs when asked. On a STOCKOUT, snapshot and move to another zone or a better GPU instead of waiting, but create the new GPU VM only after the user approves it explicitly
   _Instead of:_ Leave VMs running, wait for capacity, or silently create new ones · _Why:_ Cost; L4 stockouts are frequent; auto-mode blocks VM creation without approval — “is the vm created? else make it with a better gpu?” (2026-11-24)
5. **Long VM jobs** — Detach long VM jobs with setsid nohup ... < /dev/null and keep polling them, reporting progress and stalls (snapshot 'terminated', boot not done, installs backtracking) without waiting to be asked
   _Instead of:_ Start a job and go quiet, or block on a hung ssh --command · _Why:_ The user repeatedly had to ask whether snapshots, boots and runs were done — “keep checking if it ever stalls” (2026-11-24)
6. **Real2sim order** — Validate in stages: start from one demo of a public UMI dataset (not own capture), check reconstruction accuracy before any replay or Steel scene, get object physics by one-to-one matching each reconstructed object to a public database with measured mass (YCB + ABO, CLIP kNN + size, small classifier) and refine afterwards, and train a toy example end to end (with README maths first) before thousands of shape/size/mass variations with VLA + RL
   _Instead of:_ Jump straight to own data capture, estimate mass from geometry, or run full-scale training · _Why:_ Validate each step cheaply before a big run — “training first with toy example has to be done before” (2026-11-24)
7. **Configurability** — Make every part configurable as YAML nodes plus Python, managed with uv. Use very small SOTA models so verification stays fast
   _Instead of:_ Hard-coded scripts, argparse flags, pip/requirements.txt · _Why:_ The user wants to swap and evaluate many papers per stage — “also I want eveyrthing to be configuranble in python and uv” (2026-11-13)
8. **Repo scope** — Commit only files from /home/proto/robot-learning; keep .venv/, runs/, __pycache__/, logs and .claude/ in .gitignore. Before making the repo or a page public, scan all commits for keys, tokens, emails, IPs and the cloud project ID
